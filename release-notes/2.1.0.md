# PixelFlux 2.1.0

A feature release adding a virtual camera for client webcam uplinks, resolving the software H.264 encoder at build time, and reworking the NVENC and host-capture paths for lower latency, alongside a full license inventory of both build configurations.

## Breaking Changes

- **`use_openh264` setting removed** : the software H.264 encoder is now chosen at build time, not per capture. The default `gpl` feature encodes every CPU H.264 session with x264; a `PIXELFLUX_ENABLE_GPL=0` build (`--no-default-features --features openh264`) encodes them with Cisco OpenH264 instead. `use_cpu` is once again purely the caller's software/hardware choice
- **`pixelflux.SOFTWARE_H264_ENCODER`** : new module attribute reporting `"x264"` or `"openh264"` for the installed build; `pixelflux.SOFTWARE_H264_FULLCOLOR` reports whether that encoder carries 4:4:4 (x264 does, OpenH264 does not)

## New Features

- **Virtual Camera** : new `VirtualCamera` / `VirtualCameraSettings` classes turn a client's webcam uplink into a V4L2 capture device for applications. Encoded frames of any supported codec (H.264, VP8, VP9, AV1, HEVC, MJPEG) are pushed with `cam.push(buffer, codec, keyframe=...)` and decoded off the GIL on the camera's own thread; a browser sending JPEG is passed through as an MJPEG device with no decode. `push()` returns immediately and signals `KEYFRAME_WANTED` when the decoder needs an IDR, and `VirtualCamera.shm_layout()` reports the ring's byte layout for the interposer ABI test
- **Virtual-camera sinks** : the decoded stream is served to the Selkies V4L2 interposer over a shared-memory ring (no privileges), and mirrored to a `v4l2loopback` output device and a PipeWire `Video/Source` node where those are available (`libpipewire-0.3` is loaded at run time; there is no build-time PipeWire dependency)
- **Cursor delivery cap** : `cursor_size_cap` defaults to 128 on both backends, the most a browser shows as a cursor, so an application's own sprite (a game's 128px pointer) travels whole instead of being downscaled to the theme's size; larger sprites are still downscaled to the cap
- **KWin session screens** : a nested KWin session's screens are grown and removed on demand as `zkde_screencast_unstable_v1` virtual outputs (`add_app_screen`, `remove_app_screen`, and `app_screen_control_available`, which proves the rung by growing a probe screen and giving it back, since a stock KWin serves the request without registering the output), each held open by its own connection for as long as the screen should exist, and arranged through `kde_output_management_v2` (`set_app_screen_layout` falls through to it where `zwlr_output_management_v1` is absent); their scale follows the capture output's, which the host window's preferred fractional scale carries. The KDE output protocols are vendored under `protocols/`, newer than the copies the `wayland-protocols-plasma` crate bundles, because KWin sends a mode `flags` event those copies do not know
- **OpenH264 striped encoding** : in a `PIXELFLUX_ENABLE_GPL=0` build, OpenH264 now backs the striped path as well as full-frame — one encoder instance per stripe, with the same per-stripe wire header as x264 — so striped and full-frame sessions, CRF and CBR, and live bitrate/quality changes all work without libx264

## Encoding & Pipeline

- **NVENC direct dmabuf registration** : on the Wayland zero-copy path, capture dmabufs are registered with NVENC in place (pitch-linear as a device pointer, 4-channel surfaces as CUDA arrays) rather than copied per frame with `cuMemcpy2D`; set `PIXELFLUX_NVENC_DIRECT=0` to fall back to the copy path
- **Packed readback upload with hardware colorspace conversion** : the readback (non-zero-copy) NVENC path uploads packed BGRA/RGBA and lets the encoder do BT.709 conversion, cutting per-frame encode-thread CPU on that path
- **Shared primary CUDA context** : NVENC sessions on one device share a single primary CUDA context and query device caps up front (a 4:4:4 request the device cannot honor downgrades to 4:2:0, and a size past the device limit falls back to software with a clear message)
- **x264 reopens on an fps change** so its VBV and bitrate track the new frame budget instead of drifting

## Resilience & Fixes

- **Host-capture layout is applied without blocking the event loop** : layout requests to an external compositor are submitted non-blocking and reconciled on a later tick against a ledger, so a resize or teardown no longer stalls the calloop; a host that keeps its own mode (a refusal, no output-management protocol, or no answer by the deadline) has the capture re-sized to the mode it actually runs, and the refusal becomes a `capture_state` caveat
- **A cancelled screen configuration is rebuilt rather than refused** : `zwlr_output_configuration_v1` cancels whatever is in flight when the compositor's own state moves, which is the same moment a screen is arriving or leaving. That says the serial went stale, not that the plan was rejected, so the configuration is rebuilt against the new state for as long as a time budget allows; a session screen's mode and scale applied while screens change no longer fall back to a capture-side scale
- **A display's tracker follows its screen's scale** : a display cut from a screen kept the scale its damage tracker was built with, so a live DPI change drew the session at the old scale until the display was resized: magnified into a corner after a change down, a quarter of the screen after a change up. The tracker is rebuilt when the screen's scale changes, as it already was when the display's size did.
- **Surface-backed cursors are answered on commit** : pixelflux now services the frame callback of a client's cursor surface and delivers the sprite when it commits, fixing frozen cursors for Xwayland and libwayland-cursor clients under host capture
- **`capture_state(display_id)`** reports `(state, last_error)` and records why a pipeline went down (no output, host connect failure, encoder fallback, a refused GBM resize, host death); `get_realized_geometry` returns `None` on a genuine timeout rather than a stale size
- Bgr888 shared-memory frames swap red and blue per the wire format so client colour is correct on that path

## Build & CI

- **Software H.264 is a build-time license switch** : the default build links GPL-2.0-or-later `libx264`; `PIXELFLUX_ENABLE_GPL=0` substitutes the BSD-licensed, vendored OpenH264 and pulls in no copyleft component. A notice at install time states which posture was built
- **License inventory** : `LICENSES.md` documents every crate and native library — linked, vendored, and run-time-loaded — of both the default (`gpl`) and `PIXELFLUX_ENABLE_GPL=0` builds. `scripts/check-licenses.py` and `pixelflux/deny.toml` gate both configurations, run by the new `Licenses` workflow; a crate that links, loads, or vendors native code must be described before the check passes
- **Minimum Rust raised to 1.89**
- OpenH264 crates are also dev-dependencies, so the OpenH264 tests run under the default build (`cargo test --lib`, and `cargo test --lib --no-default-features --features openh264` for the GPL-free graph)
